# 书签 Hub 界面优化策略（分阶段）

> 日期：2026-10-10 · 作者：strategy-writer（T2）· 基线：`995838e`（外壳 `bh-shell-v71`）
> 输入：`docs/hub-ui-audit.md`（T1）、`README.md`、`templates/index.html`、`static/app-v3.css`、`tests/`
> 范围：只给策略，不改代码、不部署。文中行号均按上述基线核对过。

---

## 0. 结论先行

**还有优化空间，但不在视觉，也不在架构，而在「管理闭环」和「触屏 / 键盘的可达性」。**

起始页最核心的那条路径已经成熟：打开即聚焦、直接打字就搜、搜的是全部收藏而不只是首页、像网址就直接开、「常用」一行、组件不挤占首屏、加载 / 断网 / 锁定都有区分。「纸与墨」配色和科幻层（v71）刚定型，这次不再动。

剩下的缺口集中在三处，按重要性排：

1. **手机上首页图标没法管理**：触屏下图标的「···」被 CSS 整个隐藏（`static/app-v3.css:1357`），想在首页改、移除、删除一个网址，只能先把密度换成「卡片」，或者跑到分组页切成列表视图。
2. **编辑弹窗里不能删除**：网址弹窗和站点弹窗的底栏只有「取消 / 保存」（`templates/index.html:625-627`），删除只在分组页卡片的「···」里有。首页上发现一个死链，要先走到它所在的分组页才能删。
3. **首页搜索结果超过 6 条就没路可走**：下拉最多列 6 条（`HOME_SEARCH_LIMIT = 6`，`index.html:8132`，注释原文是「再多就该用 ⌘K 了」），可是没有「查看全部」，手机上也没有 ⌘K；在首页搜索框里打到一半按 ⌘K，已经输入的字还会被清空（`index.html:5877`）。

这三项都能在现有单文件结构里做完，不加页面、不加标签页、不碰数据模型。其余建议按 P1 / P2 排在后面，部分要先在真机上确认。

## 1. 背景与约束

| 项 | 现状 | 对策略的约束 |
|---|---|---|
| 产品定位 | 浏览器起始页：**收藏为主**，站点看板与签到为辅（README「收藏首页 = 浏览器起始页」） | 优先改「打开 / 找到 / 整理网址」；看板、签到只做入口层面的小调整 |
| 后端 | 单文件 Flask `app.py`（约 7.2k 行），数据落在 `config.json` 和 `data/*.json` | 本策略不需要新接口：删除、移动、排序接口都已存在 |
| 前端 | 单模板 `templates/index.html`（约 8.9k 行，内联脚本）+ `static/app-v3.css` + `static/halo-motion.js`，无构建步骤 | 不引入框架、不拆文件；新交互要复用现有函数（`undoableDelete`、`placeMenu`、`openOmni`、`ARRANGE` 状态机） |
| 缓存 | Service Worker 外壳是 cache-first + 版本号（`static/sw.js:48`，当前 `bh-shell-v71`） | 每一批前端改动都把版本号 +1，否则用户拿到的还是旧外壳 |
| 偏好 | Cookie + 登录后同步到 `deck.json` 的 `prefs`（名字有白名单） | 新偏好要么不加，要么同时进白名单和测试 |
| 测试 | `tests/` 下约 70 个单测文件（有些在 node 里真跑模板脚本）+ `tests/browser/run_all.py` 八套 Playwright 回归 | 每项建议都要写清会碰到哪些断言 |
| 既有决定 | 不新增服务 / 标签页 / 组件；视觉沿用「纸与墨」+ 科幻层 | 本文不推荐任何新页面或新视觉风格 |

## 3. 怎么排优先级

每项按三个问题打分，顺序就是权重：

1. **是不是核心路径上的断点**：打开网址、找网址、整理网址时，会不会走不下去、被迫绕路，或者丢掉已经输入的内容？
2. **把握有多大**：从源码就能确定的排前面；要真机或截图才能确认的往后放。
3. **成本与回归面**：是否只改 `index.html` + 少量 CSS？碰到的测试是否少而明确？

- **P0**：核心路径断点 + 源码可确认 + 小改动。一个批次就能做完。
- **P1**：体验提升明显，但要先在真机上确认、要做交互取舍，或工作量中等。
- **P2**：低频场景、需要用户先拍板，或纯代码整理。

工作量是**相对值**：S ≈ 只改一两个函数加几行样式；M ≈ 新增一段交互逻辑和对应测试；L ≈ 跨多个模块或要改历史 / 路由语义。

## 4. P0：低成本补闭环（建议一批做完）

### P0-1 编辑弹窗里原地删除（网址 + 看板站点）

- **现状证据**：`#linkModal` 底栏只有 `#linkCancel` / `#linkSave`（`index.html:625-627`），`#bmModal` 同样没有删除；分组弹窗有 `#groupDelete`（`:772`，`:7382` 只在编辑时显示）。首页图标菜单里只有「从首页移除」（`:3324-3328`），没有「删除」。
- **场景**：在首页或搜索结果里发现一个网址已经失效，想直接删掉。
- **调整**：
  - 编辑已有网址时（`linkEdit.lid` 不为空），底栏左边加一个红色文字按钮「删除网址」（复用 `.modal-actions .spacer` 推开），新建或批量模式下不显示。
  - 点击后：关闭弹窗 → 调用现有的 `deleteLink(gid, lid)`。它已经通过 `undoableDelete` 给出带「撤销」的提示条，所以**不再弹二次确认**，和分组页里删除的行为一致。
  - `#bmModal` 在编辑时同样加「删除站点」，走 `deleteBm(i)`。
  - 未保存的修改：点删除就等于放弃这些修改，不需要额外提示（反正撤销能找回原条目）。
- **收益**：首页删除一个网址，从「找到所在分组 → 进分组页 → 找到那一行 → ··· → 删除」缩短为「··· → 编辑 → 删除」，而且全程不离开首页。
- **涉及**：`templates/index.html`（弹窗 HTML 约 `:625`、`openLinkModal` `:7209`、站点弹窗打开函数）、`static/app-v3.css`（`.btn.danger` 已有，可能不用改）。
- **工作量**：S。
- **依赖 / 回归风险**：无前置依赖。注意 `deleteLink` 里重画用的是 `renderLibrary` + `renderHome`，弹窗要先关再删，否则焦点会还给一个已经被移除的元素。目前没有单测直接断言 `#linkModal` 底栏的按钮，要新增用例；`tests/test_revisit_refresh.py:72` 把 `#linkModal` 当作「有弹窗打开」的替身，不受影响。
- **验收标准**：
  1. 编辑已有网址时能看到「删除网址」，新建 / 批量时看不到；
  2. 删除后提示条出现「撤销」，5 秒内撤销能回到原分组的原位置；
  3. 首页、分组页、搜索结果三处打开的编辑弹窗行为一致；
  4. 未解锁时按钮不可达（弹窗本身就有 `guardAdmin()` 拦截）；
  5. 新增单测覆盖「编辑时显示 / 新建时隐藏 / 点击后调用 `deleteLink`」。

### P0-2 触屏首页图标的管理入口：编辑态下轻点图标弹出操作菜单

- **现状证据**：`app-v3.css:1357` 在 `hover: none` 时隐藏 `.tile-menu`。编辑首页（`ARRANGE.on`）时图标没有链接，轻点**什么都不发生**：`#homeList` 的编辑态 click 处理只认「−」按钮（`index.html:5729-5733`）。现在手机上的绕路是：首页工具「⋯」→ 切到「卡片」密度 → 卡片「···」→ 编辑，改完再切回原来的密度；或者进分组页切到列表视图。
- **场景**：手机上把首页当起始页，想改某个图标的名字、复制网址、移出首页或删掉它。
- **调整**（先做低风险版本，长按放到 P1-1）：
  - 编辑态下，**轻点**（`pointerup` 时没有进入拖动、位移小于拖动阈值）图标，就在它旁边弹出和桌面「···」**同一份**菜单内容（编辑 / 复制网址 / 前往分组 / 从首页移除，再加 P0-1 的删除），定位复用 `placeMenu`。
  - 长按照旧是拖动（`ARRANGE_HOLD_MS` 计时器不变），左上角「−」照旧移除。
  - 键盘：编辑态下图标获得焦点时按 `Enter` 打开同一菜单（顺便补上桌面编辑态的键盘入口）。
  - 编辑态说明条（`#homeArrangeBar`）的文字加一句「轻点图标可编辑」，触屏上才显示。
- **收益**：手机用户留在首页就能完成全部图标管理，不需要知道网址属于哪个分组，也不用换密度。
- **涉及**：`templates/index.html`（`ARRANGE` 指针处理 `:5708-5733`、`homeTileHtml` / `tileExtrasHtml` `:3300-3318`、菜单 HTML 抽成可复用函数）、`static/app-v3.css`（菜单在编辑态的定位）、`README.md`（「触屏上图标没有『···』」这句要改）。
- **工作量**：M（主要是区分「轻点」和「开始拖动」，以及菜单关闭后焦点和编辑态的衔接）。
- **依赖 / 回归风险**：和拖动共用指针事件，最大的风险是**误触**：手指按下稍一移动就既开菜单又开始拖。必须用「抬起时没进入拖动」来判断。`tests/test_home_layout.py:272` 断言编辑态的 HTML **不含** `tile-menu`，所以菜单应该做成按需挂载的浮层，不要放回图标的 DOM 里，或者同步改这条断言。浏览器回归 `tests/browser/verify_0926.py:281` 点的是图标视图下的「···」，不受影响。
- **验收标准**：
  1. 390×844 触屏视口下：进入编辑 → 轻点图标出现菜单；按住约 0.25 秒后滑动是拖动，**不**弹菜单；
  2. 菜单里每一项在编辑态下都能正常执行，执行后仍停在编辑态，或按预期退出；
  3. 桌面编辑态：鼠标单击图标同样出菜单；焦点在图标上按 `Enter` 出菜单、`Esc` 先关菜单再退出编辑；
  4. `prefers-reduced-motion` 下菜单不做动画；
  5. Playwright 用 `has_touch=True` 的上下文补一个用例。

### P0-3 首页搜索：「查看全部结果」接到全局搜索，⌘K 带上已输入的字

- **现状证据**：下拉最多列 6 条收藏（`HOME_SEARCH_LIMIT = 6`，`index.html:8132`；`homeSearchRows` 在 `:8208-8215` 截断），后面直接接「用 xx 搜索 / AI / 笔记」，没有提示还有更多结果；⌘K 预填只认 `#bmSearch`（`:5877`）；手机上找不到全局搜索的入口（`app-v3.css:1747` 隐藏了 `.omni-trigger`）。
- **场景**：搜一个常见词（例如某个服务商名字，对应十几个子站点），想要的那个排在第 7 条以后；或者在桌面上打到一半想切到命令面板。
- **调整**：
  - `omniSearch(text)` 的命中数大于 `HOME_SEARCH_LIMIT` 时，在收藏结果的最后加一行「查看全部 N 条结果 ⌘K」（手机上不显示 `⌘K` 字样），选中后执行 `openOmni(当前输入)`，并清空首页搜索框；这一行可以用方向键选中，回车执行。
  - ⌘K 的预填改成：焦点在 `#homeSearch` 时取它的值，在 `#bmSearch` 时取那个值，否则为空。
  - **不改**「下拉不过滤网格」这个模型：起始页的搜索是「找到就走」，网格跟着闪会打断习惯，而且下拉搜的是全部收藏，范围比网格大。
- **收益**：第 7 条以后的结果在手机上有了入口；桌面上从首页搜索切到命令面板不用重新输入。
- **涉及**：`templates/index.html`（`homeSearchRows`、`homeSearchRowHtml`、`runSearchRow`、全局 keydown `:5873-5879`）、`static/app-v3.css`（新的那一行复用 `.home-search-row` 样式）。
- **工作量**：S。
- **依赖 / 回归风险**：`HOME_SEARCH.active` 的方向键循环会把新增的行算进去，要确认它不是 `noteState` 那样的「不可选中行」。`tests/test_ui_polish.py`、`tests/test_library_home_ui.py` 和浏览器回归 `verify_polish.py` / `verify_0926.py` / `verify_ask.py` 都碰首页搜索下拉，行数或顺序的断言可能要更新；`tests/test_omni_search.py` 测的是 `omniSearch` 本身，不受影响。全屏的全局搜索面板在手机上的样式已经有了（`app-v3.css:1752-1753`）。

### P0-4 键盘小修：编辑首页时不抢焦点

- **现状证据**：`homeSearchReady()`（`index.html:8184-8187`）没检查 `ARRANGE.on`；编辑态下焦点停在图标上（`tabindex=0` 的 `div`，不算「正在输入」），按任意字母都会把焦点送到搜索框。
- **场景**：桌面上用方向键整理首页时误按了一个字母，焦点跳走，下一次按方向键就挪错地方。
- **调整**：`homeSearchReady()` 里加 `&& !ARRANGE.on`。
- **收益**：键盘整理不再被打断。
- **涉及**：`templates/index.html` 一行。
- **工作量**：S。
- **依赖 / 回归风险**：基本没有。`homeSearchReady` 还被其它地方调用时（例如首次聚焦），编辑态本来就不该聚焦搜索框，行为一致。
- **验收标准**：编辑态下焦点在图标上按 `a`，焦点不动、搜索框为空；退出编辑后，在首页直接打字照旧进入搜索框。补一条 node 单测。

## 5. P1：明显提升，但要先做验证或取舍

### P1-1 触屏长按图标直接弹出操作菜单（不必先进编辑态）

- **现状证据**：同 P0-2。平时（非编辑态）长按图标，会弹出浏览器自带的链接菜单（新标签页打开、复制链接等）。
- **场景**：手机上「长按改一下」是最直觉的操作。
- **调整**：非编辑态下，触屏按住约 450ms 且没有滚动，就弹出 P0-2 那份菜单，底部以抽屉形式展示；同时在 `.tile-link` 上设 `-webkit-touch-callout: none`，并拦截 `contextmenu`，屏蔽浏览器原生菜单。菜单里补一项「在新标签页打开」，弥补原生菜单被屏蔽后少掉的功能。
- **收益**：手机上编辑一个首页图标只需两步（长按 → 编辑），而 P0-2 要四步（工具 → 编辑 → 轻点 → 编辑）。
- **涉及**：`templates/index.html`（`#homeList` 指针事件、菜单浮层）、`static/app-v3.css`。
- **工作量**：M。
- **依赖 / 回归风险**：依赖 P0-2 的菜单浮层。**屏蔽原生长按菜单是一次取舍**：有人习惯长按「在后台打开」。iOS Safari 长按链接还会出现预览，`touch-callout` 能否完全压住要实测；长按和滚动手势也可能打架。和编辑态的「按住拖动」要保持区分（编辑态里长按仍是拖动）。
- **验收标准**：iOS Safari 和 Android Chrome 真机上：长按出菜单，没有原生预览；滑动页面不会误触发；轻点仍然直接打开网址；菜单「在新标签页打开」可用。**真机通过之前不合入。**

### P1-2 首页图标网格用方向键移动（每个图标只占一个 Tab 停靠点）

- **现状证据**：每块图标里有两个能获得焦点的元素（`<a class="tile-link">` 和 `<summary>`，`index.html:3302-3318`）；40 个图标约 80 次 Tab。月历已经实现了方向键网格（README「整张月历只占一个 Tab 停靠点」），编辑态也有方向键。
- **场景**：桌面上不碰鼠标、只用键盘打开某个图标。主路径是直接打字搜索，这条是给不想搜索、想按位置挑的人用的。
- **调整**：
  - 每个分组的 `.tile-grid` 采用 roving tabindex：只有当前那个 `.tile-link` 是 `tabindex=0`，其它是 `-1`；`←/→` 前后移，`↑/↓` 按 `fitHomeGrid` 量出的列数跨行，`Home/End` 到本分组首尾。
  - `summary`（「···」）设为 `tabindex=-1`，用 `Shift+F10` 或菜单键打开当前图标的菜单；`?` 表里写出来。
  - 先只在**单个分组内**移动，`Tab` 跳到下一个分组的网格，避免跨分组的列对齐问题。
- **收益**：键盘遍历首页的按键次数从「每个图标两次 Tab」降到「每个分组一次 Tab + 方向键」。
- **涉及**：`templates/index.html`（`homeTileHtml`、网格 keydown、`fitHomeGrid` 的列数）、`SHORTCUTS`。
- **工作量**：M。
- **依赖 / 回归风险**：和编辑态的方向键处理（`:5734`）共用 `#homeList` 的 keydown，要用 `ARRANGE.on` 分流；读屏要能正确朗读（每个网格加 `role="group"` + `aria-label=分组名` 就够了，**不要**套完整的 ARIA grid 语义）。分组页的图标视图（`linkTileHtml`）是同一套 HTML，要决定是否一起改。
- **验收标准**：Playwright 统计「从搜索框 Tab 到第 3 个分组第 1 个图标」的按键次数，改前改后对比并写进提交说明；方向键在每行末尾按列数正确换行；`Shift+F10` 打开菜单、`Esc` 关闭后焦点回到图标；编辑态行为不变。

### P1-3 手机弹窗：头部加 ✕，阻止背景跟着滚

- **现状证据**：各弹窗的 `.modal-head` 都没有关闭按钮（`index.html:503-765`）；手机上弹窗是底部抽屉（`app-v3.css:1756-1757`），关闭只能点上方约 10% 的遮罩、点底部「取消」或按 Esc。`.modal` 没有 `overscroll-behavior: contain`。
- **场景**：单手操作时想放弃编辑；在长弹窗（自定义首页、导入）里滑到底以后继续滑。
- **调整**：
  - 只在 ≤760px 时，`.modal-head` 右侧显示一个 ✕ 图标按钮（`aria-label="关闭"`，触控区域 ≥ 44px），行为和该弹窗的「取消」完全一样（包括「有未保存修改时晃一下提示」的 `nudge` 逻辑）。最好在打开弹窗的公共路径里统一注入，不要逐个弹窗手写。
  - `.modal` 加 `overscroll-behavior: contain`。**不**采用 T1 建议的给 body 加 `overflow: hidden`：iOS 上锁 body 会让页面跳回顶部，而这个仓库在其它滚动列表上一直用的是 `overscroll-behavior`。
- **收益**：手机上关闭弹窗的路径变短；长弹窗滑到头不会带着背景一起滚。
- **涉及**：`templates/index.html`（弹窗打开 / 关闭的公共函数）、`static/app-v3.css`。
- **工作量**：S～M（取决于各弹窗关闭逻辑是否统一）。
- **依赖 / 回归风险**：每个弹窗的「取消」逻辑并不完全一样（有的要检查是否有未保存修改），✕ 必须调用同一个处理函数。`tests/test_menu_layering.py` 有层级相关断言。
- **验收标准**：390×844 下每个弹窗都有 ✕ 且行为等于「取消」；桌面上不显示；iOS Safari 真机上长弹窗滑到底，背景页面不动。

### P1-4 手机分组页回首页：更好找，当前分组标签滚进视野

- **现状证据**：底栏「收藏库」一点就回首页（`index.html:1709`），但界面上没有任何提示；分组页页头的小标签是纯文字「收藏库 · 分组」（`:3216`）；标签行 `.chip-row` 横向滚动（`app-v3.css:363`），重画后没有把当前标签滚进视野。
- **场景**：手机上从首页点进一个靠右的分组，看完想回首页。
- **调整**：
  - 只在手机上，把分组页页头的小标签改成可点的「‹ 收藏首页」（看板页同理），执行 `openLibPage('@home')`；
  - `renderLibNav` 之后把 `#libChips` 里当前的标签用 `scrollIntoView({ inline: 'nearest', block: 'nearest' })` 滚进视野。
- **收益**：回首页有一个看得见的入口；在分组之间切换时，当前位置一眼可见。
- **涉及**：`templates/index.html`（`renderLibrary` `:3205-3240`、`renderLibNav` `:2894-2911`）、`static/app-v3.css`（≤760px 规则）。
- **工作量**：S。
- **依赖 / 回归风险**：科幻层给页头小标签做了等宽 HUD 样式（v71），改成按钮后要保留这个样式；`scrollIntoView` 不能带动页面纵向滚动（必须用 `block: 'nearest'`）。
- **验收标准**：手机视口下分组页能看到并点击「‹ 收藏首页」；从首页点最右边的分组后，标签行里它完整可见；桌面上页头不变。**改之前先截一张真机图，确认标签行现在确实会跑偏**；如果不会跑偏，第二条就不做。

## 8. 暂不建议做的改动

| 改动 | 原因 |
|---|---|
| 首页搜索改成「边打字边过滤下方网格」 | 下拉搜的是全部收藏，范围比网格大；网格跟着闪会打断「找到就走」的起始页习惯。缺口用 P0-3 的「查看全部」补上 |
| 重命名数据模型（`bookmarks` ↔ `link_groups`）或把站点看板挪出收藏库 | 影响导入导出、备份兼容、API 和大量测试，用户感知不到收益；新增顶层标签页也违背「不新增页面」的既有决定 |
| 跨分组拖动排序 | 首页顺序是各分组顺序的投影（README 明确），跨分组拖动要同时改归属和两个分组的顺序，状态复杂。用 P2-2「移到分组」解决 |
| 组件列改成双列 / 沉到图标下方 | 组件列已经吸顶并自带滚动，T1 的结论不成立 |
| 重做焦点框 | 全局已有 2px 强调色描边，只需要在壁纸场景下验证对比度 |
| 极简密度加回分组标题 | 极简就是去掉分组的那一档，需要分组请用默认的「信息」 |
| 弹窗打开时锁 body | iOS 上会让页面跳回顶部；用 `overscroll-behavior` 就够了 |
| 换前端框架、拆分单文件模板 | 和「单文件 Flask + 单模板」的部署模型冲突；本文所有建议在现有结构里都能做完 |
| 新的视觉风格、新组件、新服务 / 标签页 | 视觉方向刚定型，用户已经说过「功能足够了，不新加」 |
| 为了验证效果去采集使用数据并上报 | 没有必要，见第 9 节 |

## 10. 仍需实际页面验证的结论

以下结论只来自源码，没有在浏览器里看过（T1 和本任务的环境都没装 Playwright）：

1. ISSUE-12：iOS Safari 上弹窗滑到底，背景是否真的跟着滚；
2. P1-4：手机标签行切到靠右的分组后，当前标签是否跑出视野；
3. P1-1：`-webkit-touch-callout: none` 能否完全压住 iOS 的链接长按预览；长按和滚动是否打架；
4. 壁纸场景（尤其星核、极光这类深色壁纸）下，2px 强调色焦点框的对比度是否足够；
5. HYP-01：科幻特效在低端安卓机上的实际帧率；
6. HYP-02 / P2-4：分组较多时 72px 细栏是否真的难认；
7. ISSUE-06 的另一面：首页图标很少、组件很多时，宽屏左侧的留白是否需要处理（属于审美判断，要看截图）；
8. P0-2：编辑态下「轻点」和「按住 240ms 开始拖」的区分，在真机上是否容易误触。

## 12. 策略摘要

- **还有空间，但很集中**：视觉和架构不用动，缺的是「管理闭环」和「触屏 / 键盘可达性」。
- **先做 P0（一到两次提交）**：
